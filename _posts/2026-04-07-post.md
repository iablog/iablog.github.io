Em alguns contextos, um agente de IA precisa de muito mais flexibilidade do que um menu fixo de ações pode oferecer. Pense em análise de dados: se todas as análises possíveis estiverem restritas a algumas ferramentas predefinidas, o agente fica muito limitado. O **CodeAct** surge como uma abordagem diferente e mais poderosa, em vez de escolher entre ações, o agente escreve e executa código Python diretamente.

A ideia é simples: em vez de escolher entre ações predefinidas, o modelo escreve **código Python**, e esse código é executado de verdade no ambiente. Parece uma mudança pequena, mas abre muito mais espaço para o agente expressar estratégias complexas.

## A Ideia Central do CodeAct

No ReAct, o agente pensa e escolhe uma ação de uma lista fixa. Funciona bem, mas limita o agente ao que o desenvolvedor antecipou.

O CodeAct troca esse menu por uma linguagem de programação inteira:

> Em vez de escolher uma ação, o agente escreve um programa.

O modelo gera um bloco de código Python, esse código é executado, e tudo que foi impresso no `stdout` volta como a próxima observação. O ciclo se repete até a tarefa ser concluída ou o limite de turnos ser atingido.

```
Escreve código → Executa → Captura stdout → Envia de volta → Repete
```

Numa única rodada, o agente pode chamar várias ações, usar condicionais, criar loops, toda a lógica de programação fica disponível. Além disso, o modelo passa a ser responsável por imprimir as próprias observações: se ele não der um `print()` nos resultados da execução do código gerado, não vai "ver" nada no próximo turno.

## O Ambiente de Exemplo: MiniGrid

Para demonstrar o CodeAct na prática, vamos usar novamente o **MiniGrid**, uma biblioteca de ambientes simples onde um agente precisa navegar por um mapa em grade para atingir um objetivo.

No MiniGrid, o agente ocupa uma célula do mapa, pode se mover para frente, girar para os lados e interagir com objetos como portas. Cada episódio tem uma missão textual (por exemplo, "chegar ao objetivo evitando a lava"). A biblioteca oferece vários ambientes prontos, aqui usaremos o `MiniGrid-LavaCrossingS9N3-v0`, onde o agente precisa cruzar um campo com corredores de lava. Para saber mais sobre os ambientes disponíveis, veja a [**Documentação Oficial do MiniGrid**](https://minigrid.farama.org/environments/minigrid/).

### Funções de Ação

Existe uma variável global `env` que guarda a instância ativa do ambiente. A chamada `env.step(NUM)` executa cada ação possível, onde cada número corresponde a um comportamento diferente. Para tornar o código do agente mais legível, criamos funções especializadas que encapsulam essas chamadas com nomes descritivos:

```python
def andar_para_frente():
    obs, r, termi, trunc, _ = env.step(2)
    return obs, r, (termi or trunc)

def girar_para_esquerda():
    obs, r, termi, trunc, _ = env.step(0)
    return obs, r, (termi or trunc)

def girar_para_direita():
    obs, r, termi, trunc, _ = env.step(1)
    return obs, r, (termi or trunc)

def abrir_porta():
    obs, r, termi, trunc, _ = env.step(5)
    return obs, r, (termi or trunc)
```

## As Partes Importantes do Agente CodeAct

### O System Prompt

O system prompt do CodeAct é mais longo que o do ReAct porque, além de descrever o ambiente, precisa ensinar ao modelo o **protocolo de comunicação via código**:

```python
SYSTEM_PROMPT_CODEACT = """
Você é um agente CodeAct que controla um ambiente Gymnasium MiniGrid por meio de *funções de ação* especializadas.

Resolva a tarefa (do ambiente) ESCREVENDO E EXECUTANDO CÓDIGO PYTHON.

# INSTRUÇÕES

1. Você DEVE responder APENAS com código Python delimitado entre:
<execute>
...
</execute>

2. Qualquer resposta que NÃO siga este formato será rejeitada.

3. Você tem acesso às seguintes variáveis no ambiente de execução:
   - `obs`       : a observação mais recente retornada
   - `encerrado` : indica término por qualquer motivo
   - `recompensa`: a recompensa da última ação

4. As *funções de ação* devem ser chamadas assim:
   `obs, recompensa, encerrado = <função de ação>`

5. A cada turno, seu código pode:
   - Chamar de 1 a 5 *funções de ação*
   - Usar loops, condicionais, variáveis auxiliares, etc.
   - Imprimir qualquer informação com `print()`

6. O stdout do seu código será enviado de volta como a próxima observação.

# AÇÕES DISPONÍVEIS
   - `andar_para_frente()`   -> move um quadrado à frente
   - `girar_para_esquerda()` -> gira 90° no sentido anti-horário
   - `girar_para_direita()`  -> gira 90° no sentido horário
   - `abrir_porta()`         -> abre uma porta 'D' à frente
"""
```

O prompt completo ainda contém uma seção **FORMATO DE UMA OBSERVAÇÃO**, que explica ao modelo a estrutura do `text_grid` e os caracteres usados no mapa (os mesmos da tabela acima). Esse trecho foi omitido aqui por brevidade, mas está disponível no código completo no Colab.

Dois pontos valem destaque. O formato `<execute>...</execute>` é o contrato entre o modelo e o executor: tudo fora dessas tags é descartado, o modelo pode raciocinar em texto antes de escrever o código, mas só o código dentro das tags será executado. E o `print()` como canal de observação, diferente do ReAct, o mapa não aparece automaticamente a cada passo. O agente precisa imprimir explicitamente o que quer ver.

### Os Templates de Observação

O primeiro turno recebe a missão e o mapa inicial. A partir do segundo, o modelo recebe só o `stdout` capturado da execução anterior:

```python
INITIAL_OBSERVATION_TEMPLATE = """
# OBSERVAÇÃO INICIAL

## mission
{MISSION}

## text_grid
{GRID}

Agora, *escreva código* para controlar o agente.
"""
```

```python
NEXT_OBSERVATION_TEMPLATE = """
NOVA OBSERVAÇÃO (STDOUT):
{STDOUT_LOG}
---
Agora, *escreva código* para controlar o agente.
"""
```

### O Executor de Código

Essa é a parte mais diferente em relação ao ReAct. A função abaixo executa o código gerado pelo modelo e captura tudo que foi impresso:

```python
def run_codeact_snippet(code_str, exec_globals, exec_locals):
    stdout_buffer = io.StringIO()
    old_stdout = sys.stdout
    sys.stdout = stdout_buffer

    try:
        exec(code_str, exec_globals, exec_locals)
    finally:
        sys.stdout = old_stdout

    return stdout_buffer.getvalue()
```

O truque é redirecionar temporariamente o `sys.stdout` para um buffer em memória (`io.StringIO`). Qualquer `print()` que acontecer durante o `exec()` vai para esse buffer. Depois da execução, o `stdout` original é restaurado e o conteúdo do buffer é retornado como string, que será enviada de volta ao modelo.

Vale notar que o `exec_context`, o dicionário com `obs`, `encerrado`, `recompensa` e as funções de ação, é passado por referência. Quando o código do modelo executa `obs, recompensa, encerrado = andar_para_frente()`, ele modifica esse dicionário compartilhado. O loop principal lê os valores atualizados de lá a cada turno.

## O Loop Principal

Com todas as peças montadas, o loop fica bem direto:

```python
# Reinicia o ambiente
obs, _ = env.reset()
encerrado = False
recompensa = 0.0

# Contexto de execução — variáveis e funções acessíveis pelo código do modelo
exec_context = {
    "obs": obs,
    "encerrado": encerrado,
    "recompensa": recompensa,
    "andar_para_frente": andar_para_frente,
    "girar_para_esquerda": girar_para_esquerda,
    "girar_para_direita": girar_para_direita,
    "abrir_porta": abrir_porta
}

# Cria a sessão de chat com o modelo
chat = GEMINI_CLIENT.chats.create(
    model=GEMINI_MODEL_ID,
    config={'system_instruction': SYSTEM_PROMPT_CODEACT, 'temperature': 0.3}
)

turn_num = 0
next_message = INITIAL_OBSERVATION_TEMPLATE.format(
    MISSION=obs["mission"], GRID=obs["text_grid"]
)

while not encerrado and turn_num < 20:
    # 1. Envia a mensagem ao modelo e recebe o código
    model_response = chat.send_message(next_message)
    model_response_text = model_response.text

    # 2. Extrai o bloco <execute>...</execute>
    match = re.search(r"<execute>(.*?)</execute>", model_response_text, re.DOTALL)

    if not match:
        next_message = ("Sua resposta não seguiu o formato exigido.\n"
                        "Responda com código Python entre <execute> e </execute>.")
        continue

    code = match.group(1)

    # 3. Executa o código e captura o stdout
    try:
        stdout_output = run_codeact_snippet(code, {}, exec_context)
        turn_num += 1
    except Exception as e:
        next_message = f"Erro de execução:\n{e}"
        continue

    # 4. Atualiza variáveis do loop principal a partir do exec_context
    obs        = exec_context["obs"]
    encerrado  = exec_context["encerrado"]
    recompensa = exec_context["recompensa"]

    # 5. Prepara a próxima mensagem com o stdout capturado
    next_message = NEXT_OBSERVATION_TEMPLATE.format(STDOUT_LOG=stdout_output)
    time.sleep(5.0)


# Resultado final
if recompensa > 0:
    print("\nSUCESSO: O modelo chegou ao objetivo!")
else:
    print("\nFALHA: O agente morreu ou atingiu o limite de passos!")

env.close()
```

O loop tem três mecanismos para lidar com respostas inesperadas do modelo. Se as tags `<execute>` estiverem faltando, o modelo recebe um aviso e tenta de novo sem gastar um turno. Se o código lançar uma exceção, o traceback volta como observação e o modelo pode corrigir no turno seguinte. E se o agente travar em algum estado, o limite de 20 turnos encerra o episódio. Esse tratamento de erros não é só segurança, ele é parte da comunicação entre o loop e o modelo.

## CodeAct vs. ReAct:

| Característica | ReAct | CodeAct |
|----------------|-------|---------|
| Ações por turno | 1 | 1 a N (via loops) |
| Flexibilidade | Limitada ao menu de ações | Qualquer lógica Python |
| Complexidade do prompt | Menor | Maior |
| Risco de erro | Baixo (ação inválida = fácil de detectar) | Médio (código pode ter bugs) |
| Melhor para | Ambientes simples e bem definidos | Tarefas que exigem lógica composta |

O ReAct ainda faz sentido quando o espaço de ações é pequeno e bem delimitado, e quando depurar o comportamento do agente importa, já que erros são mais previsíveis. O CodeAct vale a complexidade extra quando a tarefa exige sequências longas ou lógica condicional no meio do caminho.

## Conclusão

No padrão **CodeAct**, o modelo não só age, ele decide o que observar, e também como estruturar a própria estratégia e até como se recuperar de erros. De certa forma, o agente deixa de ser um executor de instruções e passa a ser um programador resolvendo um problema em tempo real.
